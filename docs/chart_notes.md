# RavenStack — Chart Notes

This document records provenance and caveats for every chart in `charts/`.
All charts are generated by `python/generate_charts.py`, which reads only
from `outputs/` CSV files. SQL remains the analytical engine.

---

## Chart 01 — Monthly New Account Acquisition

| Field | Value |
|---|---|
| **File** | `charts/01_monthly_account_acquisition.png` |
| **Source SQL** | `sql/03_account_acquisition.sql`, Query 1 |
| **Source Output** | `outputs/acquisition/monthly_new_accounts.csv` |
| **Metric definition** | Count of `raw_accounts.account_id` grouped by calendar month of `signup_date`, joined against the calendar month spine so zero-activity months are represented. |
| **Grain** | One bar per calendar month (Jan 2023 – Dec 2024). |
| **Important caveat** | `signup_date` is the account creation date, not necessarily the date the account started a subscription. For many accounts these dates differ substantially (see data quality check 16 and `docs/data_audit.md`). |
| **Validation** | Monthly totals sum to 500 (the full account count). Verified in `generate_outputs.py` validation block. |

## Chart 02 — Aggregate Subscription-Record MRR

| Field | Value |
|---|---|
| **File** | `charts/02_aggregate_subscription_mrr.png` |
| **Source SQL** | `sql/04_aggregate_mrr.sql`, Query 1 |
| **Source Output** | `outputs/mrr/monthly_aggregate_mrr.csv` |
| **Metric definition** | Sum of `mrr_amount` across every subscription record open in a given month. A subscription record is "open" in month M if `start_date <= month_end AND (end_date IS NULL OR end_date >= month_start)`. |
| **Grain** | One data point per calendar month. |
| **Important caveat** | This metric **double-, triple-, or N-times-counts** revenue for any account holding multiple concurrent open subscription records in the same month. Accounts routinely hold 5–14 concurrently open records. This is deliberately labeled "Aggregate Subscription-Record MRR" and never "Company MRR," "Account MRR," or "ARR." The December 2024 value of $10,734,251 appears in the chart subtitle's source note but is never presented as a standalone business KPI without this definition. |

## Chart 03 — Churn Events Over Time (Monthly)

| Field | Value |
|---|---|
| **File** | `charts/03_monthly_churn_events.png` |
| **Source SQL** | `sql/09_churn_analysis.sql`, Query 1 |
| **Source Output** | `outputs/churn/monthly_churn_events.csv` |
| **Metric definition** | Count of rows in `raw_churn_events` grouped by calendar month of `churn_date` (primary bars). Secondary line: count of *distinct* `account_id` values churning in each month. |
| **Grain** | One pair of values per calendar month. |
| **Important caveat** | Events ≠ accounts. The chart shows both series side by side specifically because 175 accounts have 2+ churn events — conflating total events with unique accounts would misrepresent churn concentration. `raw_churn_events` is the authoritative churn source of truth; `raw_accounts.churn_flag` is not used. |

## Chart 04 — Churn Events by Reason Code

| Field | Value |
|---|---|
| **File** | `charts/04_churn_by_reason_code.png` |
| **Source SQL** | `sql/09_churn_analysis.sql`, Query 2 |
| **Source Output** | `outputs/churn/by_reason_code.csv` |
| **Metric definition** | Count of churn events (rows in `raw_churn_events`) grouped by `reason_code`, ranked by event count descending. Percentage of total churn events shown inline. |
| **Grain** | One bar per reason code (6 codes total). |
| **Important caveat** | Counts are event-level (600 total), not account-level. An account with 3 churn events for "features" contributes 3 to the "features" count. The chart subtitle makes this explicit. |

## Chart 05 — Support Escalation Rate: Churned vs Non-Churned Accounts

| Field | Value |
|---|---|
| **File** | `charts/05_support_escalation_by_churn_status.png` |
| **Source SQL** | `sql/10_support_vs_churn.sql`, Query 1 |
| **Source Output** | `outputs/support/volume_and_resolution_by_churn_status.csv` |
| **Metric definition** | Escalation rate = count of tickets where `escalation_flag = true` / total tickets, split by whether the ticket-submitting account has at least one row in `raw_churn_events`. Non-churned: 145 accounts, 605 tickets, 4.0% escalation rate. Churned: 347 accounts, 1,395 tickets, 5.1% escalation rate. |
| **Grain** | Two bars (one per churn status). |
| **Important caveat** | This is an **observational association only**. Ticket timing is not scoped to before or after any churn event — a ticket submitted after reactivation is included in the "churned" group for the account's lifetime. No causal claim is made. The negligible resolution-time difference (35.74h churned vs 36.13h non-churned) is noted in the chart footer but not presented as a primary finding. |
| **Why this chart instead of resolution time** | The resolution-time difference is statistically negligible (~0.4h). The escalation-rate difference (4.0% vs 5.1%), while modest, is more visually discriminating and honest to report as an observational contrast. Both figures come from the same query. |
