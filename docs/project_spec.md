# RavenStack SaaS Analytics — Project Specification

## Purpose

This is a SQL-first portfolio project demonstrating applied analytical SQL,
relational data modelling, data-quality reasoning, and SaaS business analysis
against a realistic synthetic dataset (RavenStack, 2023-01 to 2024-12).

The central portfolio signal is:

> **SQL + relational data modelling + data-quality reasoning + business analysis.**

The project deliberately does not include ML, predictive modelling, dbt,
Airflow, or a BI dashboard layer. SQL is the analytical engine throughout.

---

## Dataset — RavenStack Synthetic SaaS

Five CSV files, placed in `data/raw/` and loaded without modification:

| Table | Rows | Grain |
|---|---|---|
| `raw_accounts` | 500 | 1 row per account |
| `raw_subscriptions` | 5 000 | 1 row per subscription record |
| `raw_feature_usage` | 25 000 | 1 row per usage event (usage_id not unique — 21 duplicate ids) |
| `raw_support_tickets` | 2 000 | 1 row per ticket |
| `raw_churn_events` | 600 | 1 row per churn event (352 unique accounts) |

Observation window: **January 2023 – December 2024**.

---

## Key Data Model Constraints

These constraints govern every downstream analysis. They are verified in
`sql/01_data_quality_checks.sql` and documented in `docs/data_audit.md`.

1. **Subscription overlap**: accounts routinely hold 5–14 concurrently open
   subscription records (`end_date IS NULL` for ~90% of rows). There is no
   clean sequential per-account plan history. This makes standard "current
   plan per account" and "net MRR retention" computations unreliable on this
   dataset; they are therefore not computed anywhere in the project.

2. **Churn source of truth**: `raw_churn_events`, not `raw_accounts.churn_flag`.
   The two signals conflict substantially (see data quality check 9). All
   downstream churn metrics use `raw_churn_events` exclusively.

3. **Feature usage temporal mismatch**: only ~22% of `raw_feature_usage` rows
   fall inside their linked subscription's active date window. Feature
   engagement is therefore analysed at the account/global level, not
   subscription-period level.

4. **Satisfaction score bias**: `satisfaction_score` is missing for ~41% of
   support tickets, and observed values only ever fall in [3.0, 5.0]. This
   field is never treated as representative.

5. **Signup-date vs first-subscription gap**: for many accounts, the first
   subscription `start_date` occurs weeks or months after `signup_date`. This
   depresses early-cohort-month retention figures and is documented as a
   structural dataset property, not an error.

## Technology Stack

| Layer | Choice | Reason |
|---|---|---|
| Analytical engine | PostgreSQL SQL | Portfolio signal |
| Data loading | `psql \copy` | Preserves raw CSV fidelity |
| Calendar spine | SQL `generate_series` view | Complete month coverage including zero-activity months |
| Output generation | Python / pandas | Reproduces SQL output CSVs when psql is unavailable |
| Visualisation | Python / matplotlib | Lightweight static chart generation for README presentation |

---

## SQL File Index

| File | Purpose |
|---|---|
| `00_load_raw_data.sql` | DDL + `\copy` load; no transformation |
| `01_data_quality_checks.sql` | 16 diagnostic checks; no mutations |
| `02_calendar_spine.sql` | `calendar_month_spine` view (infrastructure) |
| `03_account_acquisition.sql` | Monthly + segmented acquisition |
| `04_aggregate_mrr.sql` | Aggregate subscription-record MRR trend |
| `05_trial_conversion.sql` | Trial→paid conversion (sub-level + account-level) |
| `06_cohort_retention.sql` | Observed account subscription retention |
| `07_cohort_observed_value.sql` | Cohort cumulative observed subscription value |
| `08_feature_engagement.sql` | Feature usage volume, errors, churned vs non-churned |
| `09_churn_analysis.sql` | Churn events: monthly, reason, plan, repeat, refunds |
| `10_support_vs_churn.sql` | Support activity: churned vs non-churned accounts |
| `11_business_summary.sql` | Cross-analysis summary table + validation |

## Running the Project

### 1. Load raw data (requires PostgreSQL)

```bash
createdb ravenstack
psql -h localhost -U postgres -d ravenstack -f sql/00_load_raw_data.sql
psql -h localhost -U postgres -d ravenstack -f sql/02_calendar_spine.sql
```

### 2. Run analyses

Run SQL files 01 through 11 in order:

```bash
for f in sql/0{1..9}_*.sql sql/1{0..1}_*.sql; do
  psql -h localhost -U postgres -d ravenstack -f "$f"
done
```

### 3. Generate output CSVs (Python alternative when psql is unavailable)

```bash
python python/generate_outputs.py
```

### 4. Generate charts

```bash
python python/generate_charts.py
```
